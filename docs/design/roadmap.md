# Ontology, dbt, and Dataplatform: Delivery Roadmap

Forward-looking plan split out of
[ontology-dbt-dataplatform-design-architecture.md](ontology-dbt-dataplatform-design-architecture.md),
which now describes only the architecture as it stands. Nothing here is a description of
current behaviour: a phase is either explicitly marked delivered or is not built.

Phases are independently deliverable and are not a committed sequence. Each one that
changes existing behaviour gets its own decision record under
[decisions/](decisions/).

## Delivery roadmap

### Phase 0 — settle contracts and repair guidance drift

Goal: establish one accurate operating contract before adding features.

1. Implement DD-206's resolved release contract: track the release allowlist under the sibling
   `ontology-hub-publish/` directory; review generated bytes before release; pin the resulting dbt
   package by full hub commit SHA; and keep release tags as labels rather than dependency
   identities.
2. Reconcile all docs, skills, scaffold text, and examples around: `extract-schema` versus the
   compatibility dbt macro; `compile --emit --confirm-emit`; fixed publish location; and real
   runtime validation in the dataplatform.
3. Fix scaffold placeholders and tests so generated `packages.yml` and README always describe a
   resolvable immutable revision.

Acceptance criteria:

- A fresh hub and dataplatform scaffold contain no contradictory command guidance.
- A test proves the generated package pin resolves to the chosen publish topology.
- No release example uses an untagged branch for production.

### Phase 1 — add a read-only source-schema diff API

Goal: make schema drift safe to automate without coupling automation to TTL writes.

1. Extract structural comparison from `merge_with_existing()` into a pure typed comparator.
2. Add a read-only CLI surface that accepts current extracted schema and committed source
   vocabulary, with `--format json`, stable change codes, old and new values, table/column
   locations, `--fail-on-change`, no timestamps in the structural fingerprint, and no file writes.
3. Keep `import-source` as the explicit apply operation and have it reuse the same comparator.
4. Cover additions, removals, type changes, nullability changes, PK changes, malformed input, and
   deterministic JSON ordering.

Acceptance criteria:

- CI can distinguish unchanged, changed, and invalid input by exit code.
- The JSON schema is versioned.
- Diff and apply report byte-equivalent change sets for the same inputs.
- The command never writes a vocabulary or raw-sample file.

### Phase 2 — split structural introspection from profiling

Goal: detect physical drift cheaply and run expensive profiling deliberately.

1. Refactor extraction into two explicit stages: structural metadata (relations, columns, types,
   nullability, PKs, declared FKs where exposed) and optional profiling (row counts, distinct
   counts, enum candidates, samples).
2. Add an extraction profile option owned by the live job, not `EntityBinding`. Start with
   `structure` (no table scans), `standard` (current bounded samples plus current counts), and
   `deep` (reserved until query budgets and semantics are specified).
3. Emit a deterministic structural fingerprint per table and for the extraction as a whole.
4. Let the dataplatform workflow retain the last successful structural manifest as workflow
   state.
5. Profile changed tables, explicitly requested tables, and a scheduled periodic full set.
6. Add adapter tests asserting generated SQL, identifier quoting, query-count limits, and failure
   reporting.
7. Before implementing hand-rolled `INFORMATION_SCHEMA` row-count/last-modified queries, check
   whether `dbt build --write-index` has reached general availability with Fabric/Databricks
   support — consuming its Parquet index may be cheaper than adapter-specific queries for those
   facts. This is a build-vs-consume check to run immediately before this step, not a reason to
   wait.

Acceptance criteria:

- A structure-only run performs no full-table count, distinct-count, or sample query.
- An unchanged structure can skip profiling without invoking a table-scan query.
- A periodic full profile remains possible even when the structure is unchanged.
- Sample values remain subject to existing redaction and raw-sample controls.

Deferred from this phase: generic stratified sampling; ontology- or binding-driven profile
policy; a metadata warehouse; and third-party observability tooling.

### Phase 3 — implement declared-FK and enum evidence carefully

Goal: close useful source-evidence gaps without conflating declarations and inference.

1. Add adapter-specific declared-FK extraction as explicit source metadata.
2. Keep declared constraints distinct from naming-based inferred relationships.
3. Define enum evidence limits: maximum distinct cardinality; maximum bytes and values returned;
   deterministic ordering; redaction before persistence; and truncation metadata.
4. Do not run joined/FK-aware sampling by default — design it separately with explicit selected
   relationships, deterministic ordering, fan-out limits, and a query budget.

Acceptance criteria:

- Declared and inferred relationships cannot be confused in YAML, TTL, or reports.
- High-cardinality fields never cause unbounded value retrieval.
- Fabric and Databricks tests cover unsupported metadata APIs and partial permissions.

### Phase 4 — declare the Silver contract and enforce binding conformance (Gate A)

> **Delivered.** The `contract.*` diagnostic family and the closed `SilverContract` schema
> ship in `core/compiler/contracts.py`, `contract_conformance.py`, `contract_emission.py`
> and `contract_scaffold.py`. Retained below as the record of what was planned; Gate B
> (Phase 5) remains open.

Goal: make the canonical Silver model a declared artifact that a new source binds *to*, so an
ordinary authoring action can no longer reshape it. Specified in
[DD-213](dd-213-silver-entity-contract.md); that document is normative for the schema and the
full rule table, and this phase is its delivery plan.

1. Add the closed `SilverContract` schema and its packaged JSON Schema, loaded from
   `model/contracts/<domain>.contract.yaml` into frozen dataclasses — never into RDF.
2. Add the contract-load rules (`contract.property-unresolved`, `contract.column-name-collision`,
   `contract.grain-not-required`, `contract.closed-requires-preview`, and the rest of DD-213 §4).
3. Add the per-binding conformance rules to the DD-133 §5 safety kernel
   (`contract.required-property-unmapped`, `contract.property-not-declared`,
   `contract.type-mismatch`, `contract.grain-mismatch`, `contract.identity-mismatch`, …), and the
   new optional `EntityBinding` key `unmapped:`.
4. Make the contract the column authority for a governed class across **both** the source-branch
   models and the union model — not just the single-source entity model — padding every branch to
   the full contract column set with typed NULLs. Retire `conformance_bases`/`base_model` as a
   column source (`kernel.py:1487-1497`), where the union currently takes its columns from
   whichever binding sorts first by filename.
5. Emit padded columns with `include_in_change_detection: False`, and reject an `unmapped`
   property that also appears in `load.incremental.canonicalHashInputs`, so a source that later
   starts supplying the column cannot trigger a mass SCD2 re-versioning.
6. Relax `conformance.property-incompatible` for governed classes — subset-of-contract plus
   explicit gaps replaces identical-property-sets, which is what lets a partial source join a
   conformance group.
7. Add `scaffold-contract <domain>`, generating the contract from the current `CompilePlan`, with
   `BuildScope` resolving foreign-domain contracts for cross-domain relationship targets.
8. Keep an absent contract file behaving exactly as today, with one advisory
   `contract.domain-ungoverned` warning — incremental adoption, no clean break, no migration
   command.
9. Add the `contract.*` rows to `diagnostic-codes.md` in the same change, as
   `tests/test_diagnostic_catalog.py` requires.

Acceptance criteria:

- Adopting a generated contract is a provable no-op: the parity manifest is byte-unchanged.
- Adding a binding for a second source to a governed class cannot change the emitted column set,
  order, names, or types — it either conforms or blocks.
- Reordering a binding's `fields:` leaves the parity manifest unchanged.
- Renaming an ontology property whose `columnName` is pinned changes no emitted column.
- A binding that omits a contract-optional property without declaring it in `unmapped:` blocks.
- The emitted column set of a governed class is unchanged by adding, removing, or renaming a
  binding file.
- A source that later begins supplying a previously-unmapped property triggers no SCD2
  re-versioning.
- `compile --check` remains stateless and independent of Git history.
- A domain with no contract file compiles byte-identically to the release before this phase.

Deferred from this phase: Gold and MDM contracts; dbt `versions:`; any comparison against a
prior release (that is Phase 5).

### Phase 5 — add released Silver compatibility comparison (Gate B)

Goal: detect changes between two releases without adding generated authority to the hub.

1. Version the existing emitted Silver parity-manifest schema if needed.
2. Add a pure comparator that consumes two manifests or two publish roots (baseline release,
   candidate release).
3. Report deterministic categories: unchanged, additive-compatible, breaking, behavior-sensitive,
   and unknown.
4. Include model addition/removal, column addition/removal/order, canonical and physical type,
   nullability, keys, tests/constraints, materialization-relevant policy, and adapter identity.
5. Treat unknown manifest versions and unclassified field changes as blocking.
6. Emit JSON for CI and concise text for reviewers.
7. Keep semantic interpretation human-reviewed even when structure is unchanged.
8. For a domain governed by a Phase 4 contract, make the **contract file diff** the primary
   reviewable unit and the parity-manifest diff the corroborating evidence that the emit matches
   the contract, classified against the table in [DD-213 §5](dd-213-silver-entity-contract.md).
   For an ungoverned domain the manifest diff remains the only available signal.
9. Compare a **contract-relevant projection** of the manifest, not the full fingerprint: the
   manifest hashes all 15 `ColumnSpec` fields, of which the contract governs 5, so an unfiltered
   diff reads every ordinary binding edit as a contract change. The full fingerprint keeps its
   separate job of proving release reproducibility.

Acceptance criteria:

- Comparisons are symmetric where appropriate and deterministic.
- Every parity field is either classified or fails closed as unknown.
- Adapter changes cannot be silently classified as compatible.
- No baseline file is written under `model/` or `integration/`.
- `compile --check` remains stateless and independent of Git history.
- A contract change and its resulting manifest change cannot be classified inconsistently.

### Phase 6 — make hub releases reproducible

Goal: prove that a released pin identifies exactly one validated output.

1. Extend the hub release workflow to: check all selected domains; emit with `--confirm-emit`;
   validate the emitted dbt project; compare against the selected prior release; record
   compatibility output; require a human-confirmed version bump; publish from the exact candidate
   commit; and record commit, plan provenance, toolkit/refmodel versions, and manifest hashes.
2. Fail if generated output is stale relative to authored inputs.
3. Test the documented `packages.yml` pin with `dbt deps` and `dbt parse`.
4. Define hotfix policy: branch from the exact production tag; release a new immutable
   tag/artifact; update production through a dataplatform PR; forward-port the fix to `main`.
5. A breaking hotfix remains a coordinated release until the model-versioning design (above) is
   implemented.

Acceptance criteria:

- Rebuilding the same release commit produces the recorded manifest hashes.
- A tag cannot publish stale or mismatched output.
- Production and development can pin different immutable releases.
- Release automation never decides SemVer from the diff without human approval.

### Phase 7 — reduce dataplatform boundary violations

Goal: make correct hub authoring easier and incorrect downstream authoring visible.

1. Add a hub-side scaffold command, owned by the dbt-transformation skill, that creates ordinary
   dbt SQL under `integration/transforms/dbt/models/`, an authoritative properties contract,
   required `meta.kairos` fields, and optionally a binding stub referencing both paths.
2. Add a dataplatform lint command for non-generated models requiring explicit
   `meta.kairos.scope: downstream-only`.
3. Flag reserved hub-owned naming patterns and metadata claims in downstream-only models.
4. Add the lint to the dataplatform scaffold CI and PR template.
5. Keep any `models/custom/` rename as a separate, idempotent migration tested against existing
   projects — not just a change to the fresh scaffold.

Acceptance criteria:

- The happy path creates a compile-checkable contracted model without manual path wiring.
- Compiler-owned output remains immutable downstream.
- Every downstream custom model carries an explicit reviewed scope declaration.
- The documentation states that lint is a governance tripwire, not semantic proof.

### Phase 8 — build scheduled drift automation

Goal: connect the read-only primitives without putting credentials in the hub.

1. Add a dataplatform workflow that runs structure-only extraction, invokes the JSON schema
   comparator, uploads redacted evidence, opens or updates one deduplicated hub issue/PR when
   drift exists, and runs profiling as a separate non-blocking job.
2. Use least-privilege warehouse credentials and environment protection.
3. Never transfer raw samples into a PR, issue, log, or committed artifact.
4. Define ownership and recovery for partial permissions, timeouts, and unavailable warehouses.

Acceptance criteria:

- Regular `dbt build` is independent of profiling availability.
- Repeated detection of the same fingerprint updates one notification rather than creating noise.
- Invalid extraction blocks automation with an explicit error instead of looking like no drift.

### Phase 9 — document the shipped lifecycle

Goal: provide one canonical, tested data-engineer path.

Expand the existing data-engineer methodology guide rather than creating a second overlapping
one. Cross-link it from the generated dataplatform README and cover: offline/manual import and
live extraction as separate supported lanes; structure-only drift checks and optional profiling;
relation bindings versus contracted dbt models; compile check, explain, confirmed emit, and
downstream runtime tests; immutable release pins and compatibility reports; hotfix and
breaking-change handling; and the downstream-only model boundary and lint.

Acceptance criteria:

- Every documented command is exercised by an existing CLI or scaffold test.
- Aspirational model versioning is clearly marked as unavailable.
- The guide distinguishes compile success, release publication, deployment, and runtime data
  quality.

## Model-versioning design (separate effort)

Start only after Phases 5 and 6 provide real compatibility and release evidence. The design must
answer, before implementation:

1. What stable logical identity survives a model rename? (Phase 4's contract answers this: the
   entity's `class` plus its declared `modelName`. Without it, there is no such identity to
   build on.)
2. How are old SQL implementations retained without re-reading old hub state?
3. How does a binding or cross-domain relationship select a version?
4. How do sequential domain emits preserve versions owned by another domain?
5. How are latest version, deprecation date, and removal release declared? (Design around dbt's
   native `latest_version_pointer` here — confirm adapter support first.)
6. How do Gold, MDM, tests, and package consumers select the same version?
7. What migration is generated for existing unversioned models?

Until this design is accepted, breaking Silver changes require a coordinated major release.

Phases 2–3 and Phases 4–7 can proceed in parallel after Phase 0. Within the second track, issues
5–6 come before 7–8: Gate A prevents a break during ordinary source onboarding, while Gate B only
reports one after the fact, and a comparator with no declared contract reports diffs in an
artifact nobody agreed to. The lifecycle guide is deliberately last so it documents shipped
behavior rather than intent.

## Minimum first release

The smallest coherent release is: guidance correction; a read-only source-schema JSON diff; the
declared Silver contract with its compile-time conformance rules; Silver manifest comparison;
reproducible release evidence; and focused documentation for those shipped paths. Richer
profiling, FK-aware sampling, folder migration, and dbt model versioning are deferred — this
first release establishes the machine contracts those later capabilities depend on, and the
Silver contract is one of them rather than a later refinement of them.
