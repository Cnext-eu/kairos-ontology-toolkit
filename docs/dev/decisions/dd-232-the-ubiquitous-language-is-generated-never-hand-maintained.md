# DD-232: The ubiquitous language is generated, never hand-maintained

**Status:** Accepted
**Date:** 2026-09-20
**Affects:** new `core/projections/ubiquitous_language_projector.py`
(`architecture/ddd/ubiquitous-language.ttl`), new `core/projections/concept_guide_projector.py`
(`architecture/ddd/concept-guide.md`), `core/projector.py` (`ddd` post-domain block),
`scaffold/ontology-hub/kairos.yaml.template` (`projections.concept_guide.samples`),
`tests/test_ubiquitous_language.py`
**Issue:** none — asked for directly (2026-09-20): "after a domain design I would like to have the
terminology we keep as part of our DDD design in a separate vocabulary, linked to our ontology
IRI, together with a short business document holding business descriptions and samples".

### Context

Two hand-written documents exist in a real hub today: a SKOS glossary of the business's own
words for things, produced in discovery, and a "core concepts and how they relate" page — every
concept with its source name, canonical class and industry class, how the concepts connect, and
the relationship list. Both are exactly what a context engineer hands to the SMEs and the data
engineer after a domain design. Both are also snapshots. DD-071 is honest about the glossary:
*"initial, inspirational artifact … NOT an authoritative mapping kept in sync with the domain
ontology"*. The concepts page was accurate the day it was written and is not checked by anything.

Everything in those documents except the narrative is derivable: labels and comments from the
ontology, context, scope notes, examples, synonyms and invariants from the DDD overlay (DD-229),
business synonyms from the discovery glossary, source names and realised relationships from the
bindings, Silver status from the contracts and bindings (DD-230), dispositions from the class
ledger (DD-231). A hand-maintained copy of derivable facts drifts — the same argument DD-133 makes
against persisting a derived manifest, and the Lucid rule the hub's own design note reached:
*a rendering, never a source*.

### Decision

**Two artifacts, generated by every `project --target ddd`, for every hub with a class, DDD design
or not.** A domain design already produces a language worth reading back to the SMEs; a hub without
bounded contexts is grouped by domain instead.

**`architecture/ddd/ubiquitous-language.ttl`** — one `skos:ConceptScheme` in the namespace
`<common prefix of the hub's own ontology IRIs>terms#`, one `skos:Concept` per class the hub
declares (DD-231's population, ids suffixed by domain when two share a local name):

| Predicate | Source of truth |
|---|---|
| `skos:exactMatch` | the class IRI — the link to the ontology; the concept never redefines it |
| `skos:broadMatch` | the reference-model superclasses — the industry name |
| `skos:prefLabel`, `skos:definition` | `rdfs:label`, `rdfs:comment` |
| `skos:altLabel` | overlay `skos:altLabel` ∪ discovery-glossary labels linked to the class |
| `skos:scopeNote`, `skos:example` | the overlay's context-specific language |
| `skos:hiddenLabel` | the bindings' `source.relation` — the source name, searchable, not displayed |
| `skos:editorialNote` | `silver: contract|bound|unbound`, plus the DD-231 disposition when recorded |
| `skos:Collection` | one per bounded context (`terms:context-<id>`), else per domain |

A separate namespace and `exactMatch` rather than SKOS annotations on the class IRI itself: the
canonical ontology stays free of documentation concerns (DD-091 R1), the vocabulary is independently
loadable by a consumer that wants terms and not axioms, and the punning question never arises.

**`architecture/ddd/concept-guide.md`** — the generated counterpart of the hand-written concepts
page: the "three names, one concept" rule; per context (else per domain) each concept with its
canonical name and definition, what the business says, scope, synonyms, examples, industry model,
design role, invariants, sources, Silver status and relationships; the relationship reference
(`A --property--> B`, *(realised)* when a binding realises it); the concept-mapping table; stale
discovery terms; unresolved class references. What a generator cannot write — the narrative, the
workshop's words, *flow versus containment* — stays human-authored in a context's `designNote` or
a companion page that links to the guide.

**Sample values are opt-in and off by default.** The import step's `kairos-bronze:sampleValues`
are already redacted, but they are pipe-separated strings that carry e-mail addresses even in the
toolkit's own fixtures, and the guide sits in a tracked, published lane. `kairos.yaml`
`projections.concept_guide.samples: true` (with `max_samples`, default 3) turns them on, per hub,
as a decision someone wrote down; the guide's header states whether they are included. Only a
plain source-column field expression is sampled — a sample of an operator tree's input is not a
sample of its output.

**Deterministic, timestamp-free.** The Turtle carries a `# Generated by kairos-ontology <version>`
header and no generation time, for the same reason the Mermaid stamps do not (#774): the lane is
drift-gated. Discovery-glossary links that point at an IRI the ontology no longer declares are
listed under *Stale discovery terms* — DD-071's accepted drift becomes visible instead of silent.

### Consequences

After a domain design the context engineer has two review artifacts without writing them: a
vocabulary an SME can read term by term, and a guide an engineer can read before matching
columns. Both are current on every run and reviewed in the pull request beside the diagrams.
Every hub gains two tracked files under `architecture/ddd/` on upgrade; `git add` them with the
upgrade, since the drift gate does not see untracked additions.

Possible consumers, deliberately not built here: the `prompt` and `azure-search` targets could read
`skos:altLabel` for synonyms; Gold column descriptions could read `skos:definition`.

Rejected: authoring the vocabulary by hand (drifts, and duplicates the ontology's labels and
comments — the DD-071 problem again); SKOS predicates directly on the class IRIs in the domain
TTL (R1; punning; a consumer wanting terms has to load axioms); a Jinja template for the guide (the
design notes of DD-230 are built the same way in code, and one rendering style is easier to keep
deterministic); samples on by default (a tracked lane is a publication).
